# 产品开发策略 Brief Skill：知识基座设计

> 版本：设计稿 v1
> 日期：2026-08-21
> 状态：已获用户确认，待用户审阅书面规格
> 范围：Phase 0——知识资产盘点、知识基座设计与判断标准准备

## 1. 设计结论

“产品开发策略 Brief Skill”第一版不从零重做一整本橙皮书，而是把现有《快消食品产品战略橙皮书》、现有预包装烘焙新品开发 Skill 和经过核验的内部案例，提炼成面向 Brief 判断的分层知识基座。

知识基座采用渐进式披露：入口只读取路由和核心门禁；随后按当前模式和问题读取必要的阶段知识；只有确实需要时才调用专项模型、内部案例和动态调研。

Skill 的顶层决策模型是“三圈定位”：

```text
可做 ∩ 想做 ∩ 能做
        ↓
     该做的部分
```

- **可做**：市场、消费者、渠道和竞争中存在经过验证的真实机会。
- **想做**：客户有意愿，符合当前战略重点，并愿意投入资源承担相应风险。
- **能做**：供应链、设备、产线和工艺经过合理努力能够承接。

只有三圈有足够证据重叠时，才允许进入正式产品开发策略推荐。

本文的“三圈定位”（可做、想做、能做）与现有预包装烘焙新品开发 Skill 中的“三圈机会调研”（同赛道验证圈、邻近品类迁移圈、跨界趋势启发圈）不是同一个模型。前者是正式策略是否成立的决策框架，后者是进入候选方向前的调研方法；后续文件、状态字段和路由命名必须分别使用“定位三圈”和“机会调研三圈”，不得混用。

## 2. 背景与问题

原开发计划已经定义了多模式路由、Brief 章节、JSON 状态和飞书输出，但没有充分定义 AI 作出判断时所依据的稳定知识、证据边界和客户现实约束。

若直接开发程序，容易出现以下问题：

- 把行业趋势直接当成市场机会；
- 只分析消费者和竞品，忽略客户是否愿意投入；
- 只判断技术上能不能做，忽略客户战略上想不想做；
- 用过时市场数据或搜索摘要支撑动态结论；
- 把历史项目讨论稿或云端记忆线索直接写成已验证案例；
- 让快速启动模式绕过 Brief、证据和确认门。

因此，第一阶段必须先完成知识资产和判断标准设计，再进入代码实现。

## 3. 目标与非目标

### 3.1 目标

- 建立以预包装烘焙为核心、可扩展到其他预包装食品的知识基座；
- 将橙皮书中的模型、方法、工具和案例转译为 AI 可按需调用的判断规则；
- 用“三圈定位”统一工作坊、诊断和快速启动模式；
- 支持 Tavily、国外网页、国内社交媒体和电商平台的组合式动态调研；
- 建立共享记忆驱动的内部案例版本迭代机制；
- 把客户意愿、投入接受度、产线和供应链能力纳入不可绕过的判断门；
- 为后续 Skill 代码开发提供明确的文件边界、数据字段和验收用例。

### 3.2 非目标

- 不重新制作完整橙皮书、PDF、EPUB 或 DOCX；
- 不把整本橙皮书全文一次性塞入运行时上下文；
- 不把动态市场数据固化成永久知识；
- 不替代研发工程师输出精确配方、工艺参数、检测结论或量产承诺；
- 不替代现有“预包装烘焙新品开发”Skill 的三圈调研、概念、工业化审查和飞书正式交付流程。

## 4. 适用范围与边界

第一版以预包装烘焙食品为核心。可覆盖短保、中保和长保，但必须明确具体保质期与流通条件。

现烤、冷冻烘焙、甜品、饮料、乳饮和冲调产品可以作为趋势或灵感来源，但不能不经转译就作为本 Skill 的正式开发对象。

未来扩展其他食品品类时，只增加品类约束模块，不重写核心的 Brief、三圈定位、证据和确认机制。

## 5. 分层知识架构

### 5.1 五级渐进式披露

1. **入口层**：识别用户意图、当前模式和项目状态。
2. **核心规则层**：读取 Brief 门槛、三圈定位、证据状态、禁止事项和确认门。
3. **阶段知识层**：按问题读取可做、想做、能做、策略取舍或诊断文件。
4. **专项方法与案例层**：按触发条件调用 JTBD、STP、RWW、渠道—规格—价带、单位经济、生命周期、Stage-Gate 等模型，以及内部案例。
5. **动态调研层**：涉及当前趋势、竞品、价格、渠道或社交内容时，按项目实际情况选择多种来源调研。

渐进式披露减少的是无关知识，不降低必要门槛。快速启动模式也不能跳过三圈核心规则、证据标记和用户确认。

### 5.2 源知识库与运行时知识库

源知识库位于当前项目目录，作为长期维护和审校对象；后续发布 Skill 时，再把经过筛选的运行时文件复制或打包到 Skill 的 `references/` 目录。

源知识库建议结构：

```text
产品开发策略 skill 项目/
├── 产品开发策略Brief-Skill开发计划.md
├── 知识基座/
├── 内部案例/
├── 调研补充/
├── 验收测试/
└── docs/superpowers/specs/
```

## 6. 知识基座文件设计

```text
知识基座/
├── 00-知识基座说明.md
├── 01-知识路由表.md
├── 02-三圈定位总则.md
├── 03-可做：市场机会与趋势.md
├── 04-想做：客户意愿与战略承接.md
├── 05-能做：供应链能力与伸手可及.md
├── 06-三圈交集与策略取舍.md
├── 07-方法模型选择与误用边界.md
├── 08-策略诊断与评分标准.md
├── 09-案例与失败模式索引.md
├── 10-动态调研与多来源证据规则.md
└── 11-品类扩展接口.md
```

### 6.1 文件职责

- `00-知识基座说明.md`：说明定位、适用边界、证据分层、稳定知识与动态信息的区别，以及与现有新品开发 Skill 的关系。
- `01-知识路由表.md`：规定模式、阶段、触发条件、必读文件、按需文件、停止条件和 Tavily/多来源调研触发条件。
- `02-三圈定位总则.md`：定义可做、想做、能做、交集、证据要求、状态等级和正式推荐门槛。
- `03-可做：市场机会与趋势.md`：消费者、渠道、竞品、品类、趋势和市场机会的判断标准；区分趋势信号与正式机会。
- `04-想做：客户意愿与战略承接.md`：客户战略重点、明确意愿、资源投入意愿、风险接受度、决策人和不愿做事项。
- `05-能做：供应链能力与伸手可及.md`：现有设备、产线、工艺、供应商、人员、质量控制、改造投入和伸手可及等级。
- `06-三圈交集与策略取舍.md`：将三圈证据合并为策略，处理三圈不重叠、冲突和替代路径。
- `07-方法模型选择与误用边界.md`：建立问题—模型匹配表，说明每个模型的输入、输出、适用条件和不能证明的内容。
- `08-策略诊断与评分标准.md`：检查完整性、逻辑、证据、三圈闭环、可执行性和风险；评分不能替代严重问题判断。
- `09-案例与失败模式索引.md`：维护案例卡索引、可迁移方法、失败模式、证据等级和版本状态。
- `10-动态调研与多来源证据规则.md`：定义多来源调研选择、证据记录、平台观察边界和事实/信号/假设分层。
- `11-品类扩展接口.md`：规定新增品类需要补充的保质期、工艺、渠道、合规和 Brief 字段。

## 7. 三圈数据结构

后续 JSON 状态至少需要增加以下结构：

```json
{
  "three_circle": {
    "可做": {
      "status": "confirmed|signal|missing|blocked",
      "market_opportunity": "",
      "evidence_ids": [],
      "assumptions": [],
      "gaps": []
    },
    "想做": {
      "status": "confirmed|partial|missing|blocked",
      "client_intent": "",
      "strategic_priority": "",
      "investment_acceptance": "",
      "decision_owner": "",
      "evidence_ids": [],
      "gaps": []
    },
    "能做": {
      "status": "current|stretch|major_investment|cannot|unknown",
      "current_capability": "",
      "capability_gap": "",
      "equipment_or_line_change": "",
      "supply_chain_constraints": [],
      "evidence_ids": [],
      "gaps": []
    },
    "intersection": {
      "status": "recommended|conditional|not_recommended|pending",
      "strategy_fit": "",
      "trade_offs": [],
      "minimum_next_validation": [],
      "decision_reason": ""
    }
  }
}
```

三圈字段不要求一开始都有精确数字，但未知必须明确标记，不能被默认填成可行。

## 8. 多来源动态调研

动态调研采用“问题驱动、来源组合、证据分层”的方式，不限定只使用 Tavily。

### 8.1 来源组合

- Tavily：发现资料、报告、官网和线索；
- 国外搜索引擎、品牌官网、海外零售页面：海外产品和体验趋势；
- 小红书、抖音：消费语言、吃法、场景、内容和社交趋势；
- 天猫等电商平台：在售产品、规格、价格、包装和卖点表达；
- 官方报告、法规和企业资料：事实核验和一手证据。

不默认把所有平台全部搜索，而是根据项目问题选择来源。社交平台热度是趋势信号，不直接等同于销量或全国市场规模；单个平台观察不能直接升级为行业事实。

### 8.2 调研记录

每条动态证据至少记录：问题、来源类型、平台或网站、查询日期、URL、原文或页面证据、样本边界、允许表述、禁止外推范围和证据类别。

## 9. 内部案例与共享记忆迭代

共享记忆中的内容只作为案例线索，不直接作为正式事实或案例结论。升级 Skill 时执行：

1. 按主题和项目召回相关共享记忆；
2. 回到原始项目资料核验；
3. 形成内部案例卡；
4. 提炼可复用方法或失败模式；
5. 标记保密范围和对客使用限制；
6. 更新案例索引、版本记录和回归测试；
7. 对冲突或过时案例保留历史边界，不无痕覆盖。

内部案例卡至少记录项目、时间、来源、证据等级、当时阶段、可迁移经验、不可外推部分、对客限制、首次纳入版本和最近复核版本。

## 10. 模式行为

- **工作坊模式**：分别追问三圈，确认交集后形成策略和开发边界。
- **诊断模式**：检查已有方案是否遗漏某个圈、是否把信号写成事实、是否把“能做”偷换成“想做”。
- **快速启动模式**：可压缩问题和输出，但不能跳过三圈核心字段；缺口必须标注为待验证。
- **对标学习模式**：第二阶段再深化；不只分析标杆是否成功，还要判断客户是否想做、能做。
- **策略迭代模式**：第二阶段再深化；可针对单圈或三圈交集中的冲突进行补证据和重写。

## 11. 与现有新品开发 Skill 的关系

本 Skill 负责“定位三圈”：

```text
Brief → 三圈定位 → 产品开发策略 → 开发边界
```

现有预包装烘焙新品开发 Skill 负责后续的“机会调研三圈”及产品开发：

```text
策略确认 → 三圈机会调研 → 候选方向 → 正式概念 → 工业化审查 → 飞书交付
```

新 Skill 的输出应能作为现有 Skill 的规范化输入，不能重复实现后续概念、生图和工业化审查流程。

## 12. Phase 0 验收标准

知识基座完成后，必须通过：

- 路由测试：只读取当前任务需要的文件；
- 三圈测试：能识别每个圈的证据、缺口和状态；
- 反例测试：趋势好但客户不想做、客户想做但供应链接不住、产线能做但没有市场机会时，不能进入正式推荐；
- 证据测试：能区分事实、趋势信号、竞品观察和待验证假设；
- 案例测试：每个内部案例可回溯原始资料并标记版本；
- 动态调研测试：多来源记录完整，平台热度未被误写成销量事实；
- 交接测试：输出可以被现有预包装烘焙新品开发 Skill 读取；
- 回归测试：新增案例或规则后，历史项目不会出现无记录的判断漂移。

## 13. 后续阶段

本设计获用户书面审阅通过后，下一步再制定实施计划，顺序为：

1. 盘点现有橙皮书、现有 Skill 与工具的来源映射；
2. 提炼知识基座初稿；
3. 对缺口进行多来源补充调研；
4. 编写三圈测试案例和验收夹具；
5. 再修改原开发计划和 JSON Schema；
6. 最后进入 Skill 代码实现。
